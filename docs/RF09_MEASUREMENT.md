## 1. 结论先行

1. 复审报告对 RF09 的结构性判断在代码中成立，而且比报告写得更严重：`Store._write(key, value)` **完全不使用
   这两个参数**（`storage.dart:1900-1906` 只做 `_dirtyRevision++` 与 `_scheduleCommit()`），所以
   `_saveTasks()` 在 `storage.dart:2001` 算出的整库 JSON 字符串**每次任务变更后被完整生成再直接丢弃**。
2. 一次提交还会把整库编码链跑三遍以上：`_snapshotValues()` 编码 6 个键；`SaveProtocol._commitOnce` 再编码一次
   `body`，而 `body` 的**唯一用途**是喂给 `_checksum`（`save_protocol.dart:99-104`）；随后编码真正落盘的
   `payload`；`_checksum` 又对 `body` 做一次完整 UTF-8 编码。`load()` 侧还要反解后重算 `body` 校验（70-76）。
3. 实测**编码冗余不是 Debug 专属现象**：同一负载的纯 Dart 副本在 AOT 下与 JIT 同量级
   （1000/10000 规模 AOT/JIT = 0.90/0.94，见 §6），AOT 只在 n=3 因 JIT 预热未足而显著更快。
   因此不能用 RF01「Debug 构建模式差异」的解释把 RF09 一并关掉。
4. 但收益是否可达，完全取决于库规模：在用户实际演示的 3 父+2 子量级，一次编辑从命令到可见落盘
   **1.4ms**（JIT），widget 重建 **约 0.3ms 且处于测量地板**；在计划允许的 10000 任务上限，同样一次编辑
   **586ms**，其中约一半是可去掉的重复编码。**按返修计划「测不出收益则延期」的分支，小库场景应延期；
   大库场景 C1/C2 两项有据可做。**
5. 查询侧（`List.unmodifiable` 拷贝、`visibleTasks`、四象限派生）实测比保存路径低 1-2 个数量级，
   **不构成当前任何规模的瓶颈**。

### 测量设计要点

- **区分四段成本**：`sync_command`（命令同步返回前）、`pre_io`（命令下发到第一次落盘写之前，即纯 CPU 编码段）、
  `commit_settle`（提交队列直到 `flush()` 完成）、`rebuild`（widget 重建）。
- **不改动被测代码即可归因**：`Store` 构造已支持 `saveWriter`（`storage.dart:99,144`，`SaveProtocol` 注入点），
  测量器用它记录每次写盘的键名、字节数与耗时；`_snapshotValues` 各阶段则用等价副本单独立计时。
- **种子化合成数据**：`Random(seed)` 定序，混合中日文标题、~30% 带 1-3 子项、~15% 带约 600 字节笔记、
  随机截止日/提醒。实测每条任务序列化后 **436-438 字节**，1000 条 = 435,672 字节，10000 条 = 4,376,409 字节，
  与 RF04 记录里现实库（计数上限库 6.52 MiB、旧大库 10.6 MB）同一量级。
- **预热与样本数**：每格默认 3 次预热 + 7 次计时；因为单次成本随 n 线性增长，n≥1000 自动降为 4/3 次、
  n≥10000 降为 3/1 次（批量类 1-3 次）。实际样本数随每行 `samples=` 一起输出，不隐藏。
- **播种不计入测量**：建库走 `Store.debugReplaceTasks`（`storage.dart:875`），不 bump revision、不排提交，
  所以 M1-M7 的每一次计时都只包含真实用户操作路径。
- **`chain_over_minimal_x`** 等比值给出的是规模无关的相对量，可比绝对毫秒更稳。

## 5. 波动、下限与不可信读数

- 每格输出 `min/p95/max/spread`。n≥1000 的编码类测量 `spread`（IQR/中位）小、min–max 带约 ±20%，可信。
- **小 n 有明确的测量下限**：M1 在 n=3/100 的行（262µs / 2,917µs）受 jsonEncode 路径惰性 JIT 编译污染
  （n=100 只有预热 3 次；到 M2 同一负载 warm 后 snapshot 仅 21µs@3）。因此**不据 n≤100 的绝对值下任何结论**，
  只用 n≥1000 的渐进成本（≈16.5 µs/KB）与比值。
- `idle_pump` ≈160-190µs 是 widget-test 每次 pump 的框架地板；`rebuild` 与之同量级即等于「测不出差异」。
- 比值类指标（`chain_over_minimal_x`、`written_over_raw_x`、`slot_writes_med`）为**计数/字节量，与构建模式无关**，
  是本文最稳的一类证据。
- 单进程单次运行；未做跨进程重跑方差，故不把 <20% 的差异当结论。
- **计时脚本必须独占运行，不得与其他套件并发。** 本包第一版 §6 与 M7 曾与另一个测量并发，
  结果「AOT 在 1000 规模比 JIT 慢 1.51×」是 CPU 争用产物，独占复跑实为 0.90×（结论方向都会翻转）。
  §6 与 M7 两张表均已按独占复跑值更正；M1-M6 采自一次单独运行，未受影响。

## 6. JIT / AOT 模式因子（编码段，纯 Dart 副本）

`models.dart` 依赖 `dart:ui`，真实 Store 无法 `dart compile exe`，故 `rf09_encode_mode.dart` 按
`Task.toJson()`/`SubTask.toJson()` 的**同字段形状**重建负载，分别以 `dart run`（JIT）与
`dart compile exe`（AOT）跑同一脚本。它测的不是应用，只是编码链的模式敏感度。

| n | JIT 链合计 | AOT 链合计 | AOT/JIT |
| --- | --- | --- | --- |
| 3 | 707 | 188 | 0.27× |
| 100 | 4,254 | 4,691 | 1.10× |
| 1,000 | 45,850 | 41,393 | 0.90× |
| 10,000 | 456,557 | 427,689 | 0.94× |

副本 JIT 的 10k 链 457ms 与主测量器 M2 的 417ms 相差 9%，副本形状可信。

**要点**：AOT 只在 n=3 时明显更快（那是 JIT 预热代价，见 `single_warm_snapshot` 首样本 6.5ms）；
在真正会疼的规模上 **AOT 与 JIT 基本同量级（0.90-1.10×）**。这条链的成本来自字符串分配与转义，
不是 JIT 分层未热，所以**冗余编码不会因 Release 编译而消失**——与 RF01 的 Debug/Release 归因性质不同，
但也不能反过来用它证明 Release 会更慢。

> **本表曾有一版错误数据，已按干净复跑更正**：第一次跑 §6 时前台 JIT/AOT 与一个后台 widget 测量
> 并发执行，得到过「AOT 在 1000 规模比 JIT 慢 1.51×」的结果；独占重跑后实际是 0.90×。
> **教训：任何计时脚本不得与其他测试套件并发**，否则结论方向都会翻转。本表为独占复跑值。

（另一 caveat：命令行 AOT 快照与 Flutter Release 的 AOT 不是同一份编译产物，此列只作方向判断，不作设备预算数字。）

## 7. 候选点、收益上限、正确性风险与判定

| # | 候选 | 实测占比 / 上限 | 正确性风险 | 判定 |
| --- | --- | --- | --- | --- |
| C1 | 去掉 `_write(key,value)` 的被丢弃入参（`_saveTasks/_saveBoardsMeta/_saveConfig/_saveSettings` 改为 `_markDirty()`） | 每次任务变更省 7.4ms@1k、**71ms@10k**（占 visible 10.6% / 12.6%）；@3 仅 0.26ms | **低**：`value` 今日确无消费者；须保留 `_dirtyRevision++`、合并调度与 `ready/_disposed/hasStartupRecovery/credentialError` 四个门禁 | **有据可做**，随 RF08 之后。理由是大库规模上限，不是小库手感 |
| C2 | `SaveProtocol._commitOnce` 不再为校验和单独编一遍 `body`：一次编码、在其字节上求校验和 | `body`+UTF-8 校验和 = 编码链 **48.7%@10k / 49.0%@1k**（10k 省约 203ms/次） | **中**：`load()` 用「解码后重算 body 再比校验和」判定槽损坏（`save_protocol.dart:70-76`），是 OS05 启动恢复与 `discardDamagedStartupData` 的依据。改动必须**保持落盘 JSON 逐字节不变**，先补字节同一性测试，否则不得动 | **收益/改动比最高**，但必须字节同一性测试先行；与 RF04 备份/恢复交叉复核 |
| C3 | 兼容镜像不再整库重写（M3：镜像占写字节 **48%**，10k 每次 4.38 MB） | 时间上限**未测**：mock 内存写的 `io_med` 仅 0.45-2.6ms，真实磁盘写不在本环境 | **高**：镜像是冻结 React/旧版读取路径与「镜像失败由后续保存修复」依赖的对象；按键条件写要求 6 个持久化键各自的**全部**变更点（普通命令、导入、迁移、截止日提升、测试播种、凭据/config）都正确打脏标记，漏一个即旧值长驻 | **延期**。先要 RF10 在 Android/Windows 真机测出每次 9.13 MB（10k 库）落盘的实际代价，再决定 |
| C4 | 只有设置变化时不重编码整库（跨提交缓存未变键的编码串） | 只省 `snapshot` 一段：**67ms/417ms ≈ 16%@10k**；`payload` 仍须整体装配，写字节不变 | **中**：缓存失效点包括导入、WP11 迁移、`_applyDeadlinePromotion`、`debugReplaceTasks`；漏一个就是静默写旧值（正确性 bug，不是性能 bug） | **延期**。收益远小于 C1+C2，风险不成比例 |
| C5 | 读侧：缓存只读视图与 id 索引 | 上限 3.4ms+1.8ms@10k（M5），而 M7 实测 rebuild 在 n≤1000 只有 144-282µs、贴 idle 地板，10k 为 3.4ms（2 样本）；同规模 `commit_settle` 543ms → **省下来也看不见** | **中低**：但**绝不可把可修改 backing list 交给页面**；缓存视图必须在每次 `_tasks` 变更后重建，否则返回陈旧/可写列表 | **延期（无收益证据）**。若将来做，只能返回只读视图，不得暴露 `_tasks` |
| C6 | 把整库原子批次改成按键增量提交 | 写字节可降到 ~1× | **很高**：单提交点、`_savedValues` 权威性与 RF02 串行提交/RF03 完成屏障/RF04 可恢复性都建立在整库原子快照上 | **不做**。属报告明令禁止的「整体架构重写」，且以性能名义削可靠性 |

综合建议：**RF08 集成后只做 C1 + C2**（局部、不改磁盘格式、不动可靠性语义），
C3/C4/C5 按上表理由登记为有据延期，C6 明确否决。若用户实际库始终停留在几十条以内，
连 C1/C2 也只作为规模上限保障而非体验修复，**不得写进「解决了卡顿」**——RF01 的关闭结论不因此改变。

## 8. 未测与边界

1. **无真机数据**：Android/Windows 上 SharedPreferences 的真实文件写、几十 MB 写入耗时与内存峰值均未测；
   本文 I/O 段是内存 mock，**不可外推**。C3 因此无法定收益。
2. **未用用户真实库**：全部为种子化合成数据；用户当前实际任务数量未测（也不得用其数据探针），
   「用户规模下是否有感」这一问题留给 RF10 的定向验收回答。
3. **Release 对照仅覆盖编码段**（§6 纯 Dart AOT 副本），widget 构建与提交流程没有 Release/Profile 数字。
4. **动画/聚焦手感未测**：M7 在假时钟下只量同步构建工作，不是帧率；按 RF01 规则不得把
   `totalSpan` 或 widget test 耗时当 FPS。
5. **未做并发/失败路径测量**：保存失败、重试、退出 barrier、导入相交只确认了「本包不触碰」，
   它们的回归仍由 RF02/RF03/RF04 的默认测试负责。
6. **RSS 指标作废**（M6），改用写字节量表达分配规模。
7. 本包**未改任何 `lib/` 文件、未改共享文档（AGENTS/HANDOFF/CHANGELOG/ARCHITECTURE/返修计划）、
   未改 `test/review/` 下他人探针、未触碰冻结的 React/Tauri/Capacitor 端、未 push、未切 main**。
