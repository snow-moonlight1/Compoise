## 确认的问题

### RF02 / P1：导入提交期间的新编辑会丢失

入口：`lib/storage.dart:1498` 的 `applyImport`。入口检查 `baseRevision` 后仍需等待凭据与槽提交；普通命令可在这些 await 期间改变任务。随后 `_applyImportState(plan)` 将旧预览状态整体套回内存。RF-R01 暂停导入槽写入、调用 `addTasks`、再放行提交，最终新任务消失。此处不是 OS06 槽内互斥能解决的：需要 Store 层定义导入与普通命令的顺序以及同一份提交状态。还需验收重启后状态，不可仅补内存断言。

### RF03 / P1：凭据“最后一次修改”及退出完成语义不成立

入口：`storage.dart:1298` 的 `updateAIConfig`、`:1671` 的 `flush`。RF-R03 阻塞第一次新 key 写入，然后清空 key；清空值与旧 `_confirmedCredential` 相等，提前返回，先前写入完成后又把 key 恢复。RF-R02 证明凭据尚未写完时 `flush()` 已完成。Windows 正常退出等待 flush 仍可能中断凭据保存。需要统一最后意图、失败结果和退出 barrier，不能简单在 UI 添加延时。未证明真实密钥曾丢失，本轮只复现合成适配器时序。

### RF04 / P1：应用能成功导出自己无法导入的备份

入口：`storage.dart` 的 `exportJson` 与 `import_preflight.dart` 的 `maxBytes`。RF-R04 用合法的 4MiB notes 生成备份，导出成功，导入因 JSON 包装后超过 4MiB 拒绝。记录上限也可被多次合法 merge 累积突破；本地创建与导出无对应约束。限制本身是必要保护，不能直接删掉；但备份必须能恢复本应用支持的数据，不能成功提示后才让用户在另一台设备发现不可恢复。

### RF05 / P2：改变连接配置后按钮永久忙碌

入口：`screens/settings_model_request.dart:246`、`:351`。RF-R06 先成功测试一次，再发起延迟的重测，途中更换 URL；build 增加 generation 使旧响应失效，但 `_probing` 未清除，回调因 ticket 不等而直接返回，按钮持续禁用。需要由请求会话统一取消/失效和 busy 状态，不在 build 中留下不对称状态修改；生成测试也需覆盖同类路径。

### RF06 / P2：模型家族正则误当成具体能力表

入口：`ai_capabilities.dart` 的 `_responses`。所有 `gpt-5...` 在关闭思考时发 `reasoning.effort=none`；原始 GPT-5 支持 minimal/low/medium/high，而 GPT-5.1 才包括 none。RF-R07 直接证明原始 GPT-5 的请求计划错误。依据：[GPT-5](https://developers.openai.com/api/docs/models/gpt-5)、[GPT-5.1](https://developers.openai.com/api/docs/models/gpt-5.1)。这是参数合约验证，未拿真实 key 调 API。

相邻源码风险：自定义任意端点只因模型名以 deepseek 开头就发送厂商 thinking 扩展；Anthropic 正则预测尚未逐一核对的更高版本能力；短生成探测的 16-token 预算与默认思考模型可能只产生思考而无正文。返修需要具体 model/endpoint 能力依据和保守 fallback，区分截断/空正文与认证失败，不能把这些风险写成已实测厂商故障。

### RF07 / P2：合法折叠 composing range 被误判为未完成输入

入口：`widgets/task_edit_draft.dart:11`。`hasPendingImeComposition` 仅用 `isValid`；有效但折叠的 TextRange 没有待提交文本，RF-R05 却返回 true。多个保存入口复用此 helper，可能阻挡已结束输入。应同时检查范围非折叠，并验证真实中日文 IME 的完成、回车、关闭等路径。

相邻确定源码缺口：`newSubtaskController` 未加入 draft 的监听与 `isDirty`，`load()` 也不清空它。需要 widget 场景确认未按添加的子项文字在切换/关闭时如何处理，然后明确保留、提示或丢弃契约；不得把尚未验证的用户丢字写成既成事实。

## 聚焦卡顿：目前能与不能确定的部分

用户报告是小数据 Android Debug 场景；不能因为任务少排除 UI 性能，也不能凭 Debug 文件名就宣称产品完全无问题。Flutter 官方要求真实设备 profile 测量，Debug 的额外检查和 JIT 可导致停顿：[性能测量说明](https://docs.flutter.dev/perf/ui-performance)。

历史对照确认：进入/切换/退出仍是 320/300/280ms，OS23 只是集中常量；双重 `easeInOutCubic` 在 OS 包前已有，不是本轮新引入。`quadrant_transition_layout.dart:296` 的 animateTo 设置曲线，`:470` 又 transform 一次，可造成两端停留、中间速度集中，视觉“不均匀”与实际超预算帧必须分开验证。

动画帧沿 `AnimatedBuilder` 重建四个 pane/底卡；`_currentRects` 与 build 重复求 `_layoutFor`，后者测量标题；`animated_task_title.dart:247` 即使未完成任务也计算删除线 line boxes，宽度变动时重复布局。OS20 的 `List.unmodifiable(_tasks)` 每次 getter 复制容器，重复查询进一步放大大库成本。以上是可定位的执行路径，不等于它们已被证明是用户这次 3+2 场景的根因。

OS22 证据针对列表挂载/滚动，宫格样本没有循环进入、切换、退出聚焦。因此不能由其 Windows 数字推出 Android 聚焦没有回归。RF01 必须做同机同 SDK 前后对照，并用完整应用的 Release 体验验证。未有这些结果前，不给某个 OS 包定罪，不盲目回退 OS13/18/19。

## 仍需验证的边界与维护成本

- **RF08 / P2，源码风险**：`ReminderService.recordScheduleOutcome` 在重排失败时创建 attempts=0 的新账本项，Store 启动先 `rescheduleAllFuture` 再 `reconcilePending`；持续失败可能每次启动重置次数/年龄，绕开宣称的有界重试。账本持久化是未等待的队列，异常被吞，64 项满额时直接返回；需模拟重复启动、写失败与溢出验证用户是否获知。不得用测试替身调用次数代替真正状态断言。
- **RF09 / P2/P3，源码成本**：`_saveTasks` 先 JSON 编码传入 `_write`，但 `_write` 不使用 key/value 而重新保存全量快照；一次局部编辑多次编码整库，普通设置变更也保存全库。职责拆分尚未消除跨模块成本。先测序列化次数、时间和 allocations 再作小范围优化；不把它宣称为闲置聚焦的直接根因。
- **RF10 定向设备检查**：退出遇到尚在 `_applyTail` 中的桌面能力应用、真实 IME/通知、系统凭据失败、升级保留数据、托管 CI 与签名。前几项需要生命周期测试，后几项是已有设备/持有人门槛，不为每一项另造重构包。

Store 仍同时协调数据命令、导入、配置、凭据和提醒，提醒服务也混合平台实现与账本。高内聚低耦合已改善但没有完成。优先让事务、请求和退出各自有一个权威所有者；本轮不建议为“架构漂亮”大改状态管理框架或把所有可变 DTO 一次重写。
