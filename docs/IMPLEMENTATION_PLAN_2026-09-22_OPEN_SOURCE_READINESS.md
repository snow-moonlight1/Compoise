## 1. 范围与接手规则

1. 仅 Flutter Android + Windows；不改冻结的 React/Tauri/Capacitor，不增加后端、数据库、账号、云同步，不开始 WP10/WP29/UI 实验，不进行全局 UI 重画。
2. 用户认可本轮主要体验，保留该结果。只对修复影响路径补测；不能把旧 UX08 全部场景重新作为用户必须重测的前置条件，也不能把用户总体认可填写成每一条场景都有双端证据。
3. 开始先看 `git status`、AGENTS、HANDOFF。审查时是 `main / 9c622fd` 加已有未提交 R1–R5/S1 修复和文档，**禁止 reset 或覆盖其他人的改动**。当前没有远端，不创建分支、不推送或发布；提交仅遵循接手时用户授权与仓库规则。
4. 保持四个核心存储键、旧 v1 读取、三种 AI 协议、多看板/父子任务、BYOK 和本地使用。新配置字段同步模型、缺省/加载/导入白名单、UI 和三语。
5. 反例先复现再修；修复后迁到 `_test.dart` 默认回归，保留问题编号。不删除失败断言、降低检查或用现有 359 项通过代替专项验收。纯样式小修不要写只复述实现的测试。
6. 报告中的“源码确定”不是实机故障证明，“待验证风险”必须先验证才能决定修复。没有设备/签名/真实服务凭据时登记未测，不假报成功，不使用用户实际备份或密钥作为测试材料。
7. 产品改变后在 CHANGELOG 顶部追加；纯报告/计划不冒充功能发布。每包更新本计划状态表、HANDOFF、相关当前架构说明，记录结果和残余限制，历史记录保留。

## 4. 分阶段完成标准

| 阶段 | 建议达到的状态 |
|---|---|
| 用户体验尾项完成 | OS01–03 实现并验证；OS04 对 JSON 给明确结论；其余既有体验尊重用户认可 |
| 数据与关键流程可作为稳定候选 | F01–F12 中已确认的数据/配置/关键交互缺陷关闭；F13 验证有结论；保存/导入/退出/通知异常有证据，不能仅看 test 总数 |
| 可以负责任地公开源码 | 完成公开前秘密/许可证检查；固定可用工具链、基本 PR CI、准确文档与已知问题；尚未完成 P2/P3 可公开列出，不需要先做全部架构重构 |
| 稳定二进制发行 | 关键问题修复与针对性双端检查、正式身份/签名/升级和包校验完成；未验证平台能力不宣传为已验收；发布由用户另行安排 |

OS09 本机凭据保护建议在公开稳定版前完成；如延期，必须明确当前保存方式，不能继续宣称绝对隐私。OS20/21 可分阶段演进，OS22/23 可依据证据延期。不得因这些优化包延迟而把现有已经复现的 P1 问题一起搁置。

## 5. 通用验证与交付格式

在 `matrixflow-native/`，使用当前已验证 SDK；OS24 完成后以固定的新工具链为准：

```powershell
& D:/Dev_SDKs/Flutter_SDK/bin/flutter.bat test --no-pub
& D:/Dev_SDKs/Flutter_SDK/bin/flutter.bat analyze --no-pub
```

新增/改变依赖先 pub get。每个代码包先跑与修改有关的有意义回归，再运行仓库要求的默认全量和 analyze；纯文档包检查事实与链接。Android/Windows 平台包需要相应构建/设备证据，不让单元测试替代。历史基线 359 项不是固定配额，新增回归后数字应自然增长。

每包交接至少记录：包号/完成或未完成、实际基线与保护的已有改动、修了什么与为何、反例修前/修后结果、全量/analyze/平台检查、改动文件、剩余限制、下一可领取包。引用真实日志摘要，不提交含备份或密钥的原始输出。
