## 1. 建议先定哪条路

**建议保留独立的 MatrixFlow，以“找第一段实习的开源作品”为近期主目标，以小规模真实使用验证商业机会；现阶段不改为 Focus fork，不建订阅后台，不接广告。** 这是依据当前资产和目标提出的建议，最终开源、许可证和发布仍由用户决定。

Focus 证明四象限存在成熟的基础交互方案；它没有覆盖 MatrixFlow 已有的 AI 整理与父子任务流程。另一方面，AI 拆解也已经有其他产品在做，不能把“接了 AI”当成无人竞争的壁垒。值得验证的定位是：**把一段杂乱的中文待办或一个长期目标，转成可调整优先级、可以开始执行的任务；任务本地保存，AI 服务可自选。** “本地保存”不等于“模型在本机运行”：启用 AI 时，相关输入会发送给所选服务商。

对于实习，能解释模型协议、状态一致性、迁移兼容、异常恢复及评测方法的完整作品，比功能数量更值得展示。Star 可以增加可见度，但不能保证面试，也不能替代自己理解实现。已有相似软件并不会使工程实践失去价值；继续投入是否合算，取决于接下来还要完成多少关键工作以及是否有人使用。

### 2.1 它也有欠账，不能以截图代替质量判断

静态发现两个与选择底座直接相关的问题，未尝试修复：

1. **勾完成时可能显示“Task deleted”。** `task_tile.dart:211–215` 调用 `_showSnackbar('Task completed')`，但 `:92–108` 只识别精确字符串 `'completed'`，其他输入全部返回删除文案。这是可直接从调用路径确认的反馈错误。
2. **导入服务先清空再逐条解析。** `hive_service.dart:192–201` 清空 tasks/history 后再 `Task.fromJson`，无效记录被跳过。`settings_screen.dart:439–464` 只先检查顶层形状。形状合法但内容无效的备份会触发数据损失风险；正常主界面的导入入口仍待运行确认，因此不宣称已实机复现事故。

此外，当前主界面未接入所有已有 ARB 翻译文件，不能把“仓库有翻译文件”算成三语交付。以上用于估算接手成本，不代表对 Focus 全仓质量下结论。

## 3. 继续自己的，还是基于 Focus 改

比较目标固定为“保留 AI、父子任务、多 board、现有备份、Web + Native，修顺核心流程”，不以删掉现有能力来制造更低成本。

| 路线                          | 可以省什么              | 仍要做什么                                                                    | 相对工作量与结论                      |
| --------------------------- | ------------------ | ------------------------------------------------------------------------ | ----------------------------- |
| 继续 MatrixFlow，独立参考交互        | 保留数据、AI、三协议和双端互通   | 状态语义、任务行、全宽详情/象限、创建日期、入门流程及回归                                            | 最小可演示版本粗估 5–10 个开发人日，建议路线     |
| Fork Focus，移入 MatrixFlow 能力 | 可保留它的基本 UI、提醒、桌面设施 | 新增子任务/boards/AI 设置和流程、Hive schema 与旧数据迁移、兼容 ExportData、Web 对齐；补回归并承担上游问题 | 粗估 10–20 个开发人日；若保留所有现有能力，预计更大 |
| Focus 做简单个人工具，放弃双端等能力       | 需求大幅缩小，可快速试验 AI 按钮 | 仍需模型和错误处理；产品目标已变                                                         | 只有主动接受范围收缩才有优势，不能称为等价替换       |
| 给 Focus 提 PR                | 有真实上游协作记录，维护范围可小   | 对方是否接受 AI 未知；其 offline 定位可能不契合                                           | 可作为独立的开源协作练习，不能假定维护者接受整个产品方向  |

人日是静态范围估计，非报价或额度承诺；不包含原路线图的同步、Markdown、Planner，也不包含上架审核和商业后台。运行适配、设备验证可能扩大区间。当前证据不足以精确承诺哪天完成。

迁移不是“把一个 AI 文件拷进去”：Focus 的 Riverpod + Hive 与 MatrixFlow 的 ChangeNotifier + SharedPreferences 是不同状态/持久化路径；父子完成规则、ID、日期语义、导入版本、回滚等都要重新接线。MatrixFlow 已有的 React 端也不会因替换 Flutter 端而消失。

**适合独立借鉴的设计：** 完成圈与标题首行对齐，点任务看详情，普通态可拖动，低频操作放详情，宽屏使用专门布局。默认可继续用十字矩阵做总览；点象限标题进入全宽视图，下方只保留其他象限的简短标题和数量，返回恢复滚动位置。其余三个象限不必一直展开成完整大卡片。这是候选设计，尚未实现或真机验证，也不需要复制 Focus 代码。

## 4. GitHub 流量、开源和实习

**对当前目标，独立仓库更合适，但自然曝光不能作为保底获客。** GitHub 官方明确：fork 默认不显示在仓库搜索结果，需要 `fork:true` / `fork:only` 纳入。因此没有依据认为挂在 Focus 下面会自动分到它的 stars 或流量。搜索规则也不能用来推出 Trending / 推荐的确定收益。[GitHub 官方说明](https://docs.github.com/en/search-github/searching-on-github/searching-in-forks)

| 来源        | 更可控的事                                              | 不能保证的事           |
| --------- | -------------------------------------------------- | ---------------- |
| GitHub 搜索 | 清楚的中英简介、准确 topics、README 中的场景与演示、可下载且版本明确的 release | 搜索排名、推荐、star 数   |
| Bilibili  | 一个可看懂的实际演示、稳定下载入口、讲清目标用户和效果                        | 视频爆量、观看者愿意迁移待办习惯 |
| 开源协作      | 清晰贡献指南、可复现问题、小而明确的改进点                              | 上游接受 PR 或社区自发维护  |
| 实习作品      | 自己讲清一项 Bug 的状态根因、三协议兼容、评测取舍、数据保护及真实用户反馈            | 有 stars 就一定拿到实习  |

同一个视频链接到 fork 或独立仓库都能导流，但故事的可信度和受众会影响转化，不能断言播放量完全不受影响。独立项目讲自己解决了什么；fork 就清楚说明上游和自己的新增贡献，不掩盖来源。不要为去掉 fork 标签把他人的代码重新上传成“原创”。

建议面向两类人分别表达：给使用者演示“把找实习这件事拆成能开始的一步”；给开发者解释“为什么完成复选框和多选状态不能复用，以及如何验证”。不要把“帮我 star”作为产品价值的全部。

### 4.1 开源和收费不是二选一

GPL 允许商业销售；但如果分发基于 Focus 的衍生应用，需要履行 GPL 对相应源码和许可证等的要求。关闭 GitHub 仓库本身不会解除这些义务，也不能只靠改名变成闭源。完全独立实现一般交互思路与复制受保护代码不同；如果要混用具体文件/资产，应逐项核对许可，涉及商店发行时再核实具体条款。[GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#DoesTheGPLAllowMoney)、[GPLv3](https://www.gnu.org/licenses/gpl-3.0.html)

MatrixFlow 当前未发现顶层 LICENSE，尚不应宣称它已经按某种开源协议发布。建议在决定公开前梳理代码/依赖/素材来源并选择许可证；如权利归属允许，MIT 是便于使用、贡献和保留商业选择的候选，但也允许别人合法商用，不能同时期待它阻止商业复制。许可证选择不在本轮自动落地。

可以保留“开源本地客户端 + BYOK”，以后再提供可选的托管 AI 服务。收费购买省心、可用性和持续服务，源码是否公开并不单独决定是否有人付费。已放出的开源版本不能靠删除仓库收回既有许可；未来更换授权还受第三方贡献权利约束。

## 5. AI 差异存在，但不是技术护城河

Focus 没有这些 AI 能力，不代表市场没有。Goblin Tools 的 Magic ToDo 已提供自动拆解，Compiler 会把杂乱输入变成待办；其可选 Pro 为 $3/月，主要增加同步、历史、模板等持续服务，基础工具仍免费。[Magic ToDo](https://android.goblin.tools/ToDo)、[Compiler](https://goblin.tools/Compiler)、[Pro](https://goblin.tools/pro/about)

TickTick 官方国际年付价为 US$49.99，这是成熟效率工具可以收费的例子，**不是 MatrixFlow 的中国学生用户愿付同样价格的证据**。[TickTick 价格](https://ticktick.com/upgrade)

可复制的部分：四象限、调用模型、基本提示词、拆子任务。可能逐步积累的优势：任务领域的可复现评测、中文场景、用户纠正之后可理解且可控的结果、少步骤完成的交互、跨端一致性和信任。当前这些只能算积累方向，不能先宣称有壁垒。价格更便宜的竞品也不自动是“劣币”；需要用完成率、耗时和留存验证产品差异。

**不建议故意把 Base URL / 模型名设置得难填，以增加付费意愿。** 这会让免费体验失败，无法证明用户愿意买服务。保留清楚的 BYOK 高级入口和服务商预设；托管版面向不想注册供应商、充值、处理错误的人，购买“马上能用”和稳定服务。会自己填 Key 的人本来就不必全都转化为订阅用户。

这支持把 Flash 非思考模式作为后续试用的候选默认，而不是证明其普遍优于 Pro 或“分类永久 100%”。尤其不能继续宣传“四组合全部分类 100%”；此前流程通过与本次准确率是不同指标。13 项批处理耗时也不能直接当作单任务延迟。

后续若继续，只需补一组独立、人工标注的场景集：含含糊期限、无期限、长期目标、混合输入、用户反对 AI 分类等，统计接受/修改/失败和重试。截图只给出了 reasoning tokens，没有全部输入输出 tokens；因此下面成本是明确假设，不能冒充该轮实测账单。MiMo 尚未经过 MatrixFlow 的同题评测。

## 6. API 成本：官方单价与可复算情景

2026-09-08 核验，**人民币 / 百万 tokens**。用中国区按量 API 价格，不用美元汇率倒算、不用赠金，也不把 Coding/Token Plan 套餐当成应用后端可转售额度。

| 模型                   | 输入缓存命中 | 输入未命中 | 输出    |
| -------------------- | ------:| -----:| -----:|
| DeepSeek V4 Flash 高峰 | ¥0.10  | ¥3.00 | ¥9.00 |
| DeepSeek V4 Flash 空闲 | ¥0.05  | ¥1.50 | ¥4.50 |
| MiMo V2.5            | ¥0.02  | ¥1.00 | ¥2.00 |
| MiMo V2.5 Pro        | ¥0.025 | ¥3.00 | ¥6.00 |

DeepSeek 高峰是北京时间工作日周一至周五 9–12、14–18，其余空闲；产品交互不能为了省钱强迫用户等到夜间。MiMo 官网目前按上述 V2.5 系列列价，普通按量 API 与 Token Plan 额度不互通；这里不使用套餐抵扣。价格可能变动，上线前重查。[DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[MiMo 官方价格](https://mimo.mi.com/docs/en-US/price/pay-as-you-go)

假设一次“标准 AI 整理请求”输入 2,000 tokens、输出 800 tokens，全部输入未命中缓存，思考关闭，另加 **20% 重试/冗余成本**。实际一次用户动作可能触发多个请求，或一个请求处理多个任务，不把任务条数与请求数混为一谈。

```text
每月模型成本 = 请求数 × (输入 tokens × 输入单价 + 输出 tokens × 输出单价) / 1,000,000 × 1.2
```

| 每用户每月请求数 | Flash 全高峰 | Flash 全空闲 | MiMo V2.5 | MiMo V2.5 Pro |
| -------- | ---------:| ---------:| ---------:| -------------:|
| 50       | ¥0.79     | ¥0.40     | ¥0.22     | ¥0.65         |
| 300      | ¥4.75     | ¥2.38     | ¥1.30     | ¥3.89         |
| 1,000    | ¥15.84    | ¥7.92     | ¥4.32     | ¥12.96        |

可复算参数见同目录 `AI_UNIT_ECONOMICS_2026-09-08.csv`。这些不是平均用户的真实用量，也没有包含服务器、渠道、获客、售后、税费和开发时间。同样 token 数下 MiMo 便宜，但输出质量、实际生成长度和重试率未知，不能直接断言整体成本更低。

敏感性：若 Flash 每次额外生成 3,000 个计费输出 tokens，300 次全高峰月成本会从 ¥4.75 到 **¥14.47**。不是思考开关本身额外收费，而是实际计费 tokens 增加。最大输出、输入长度、并发和用户月预算都需要限制；“每月不限量”无法仅凭平均值保证盈利。

### 6.1 可以测试什么价格

先验证有人愿意持续用，再测试 **¥9.9/月的小额度省心版**，而非立刻建复杂套餐。示例边界：100 次上述标准请求约 ¥1.58 模型成本；如果测试 ¥19.9 / 300 次则约 ¥4.75。真实产品必须按消耗设预算上限，复杂长任务不能当作无限容量的一次。

仅作测算，假设渠道/支付损耗为销售额 15%（不是各商店统一费率）：

| 假设方案          | 扣假设渠道后的收入 | 模型成本  | 尚可用于服务器、客服等的金额 |
| ------------- | ---------:| -----:| --------------:|
| ¥9.9 / 100 次  | ¥8.42     | ¥1.58 | ¥6.83          |
| ¥19.9 / 300 次 | ¥16.92    | ¥4.75 | ¥12.16         |

**最后一列不是净利润。** 如果 100 个 ¥9.9 付费用户，按该假设只余约 ¥683/月支付其他成本与自己的时间。若再为 1,000 个免费用户每人提供 50 次相同 Flash 高峰请求，仅免费层就需约 ¥792/月。免费额度、留存、付费比例和重度用户分布往往比单次便宜几厘钱更影响结果。

可用 `付费人数 × (价格 × (1−渠道率) − 付费用户模型成本) − 免费层成本 − 固定运营成本 − 获客支出` 估算贡献。价格是否有人接受，需要实际试用后的付款选择验证；不虚构 1%、5% 等转化率预测。订阅也不适合承诺永久服务或用一次买断覆盖无限未来 API。

托管 AI 会增加现有纯本地架构没有的责任：共享服务商 Key 必须留在服务端，需鉴权、预算/限流、失败计费处理及支付售后。不能把运营者 Key 打进客户端。任务仍可本地保存，托管请求发送范围要讲清楚。这些只是商业路径成本说明，本轮不建设后台。

## 7. 广告从哪里来，能否养活免费 AI

程序化广告平台可以撮合广告主，无需自己逐一找品牌；典型流程是主体/应用审核、创建广告位、接入 SDK、测试、按平台结算。平台提供广告需求，并不替开发者带来使用者。

以国内穿山甲为例：官方当前要求已上架移动 App、企业资质与对公账户，明确暂不与个人开发者合作，且没有官方 Flutter 接入文档。个人学生不能把它当成“加一个插件就能收钱”；即使通过原生桥接接 SDK，也要先确认准入。其他网络须分别核验，不能把这一家规则推及全部平台。[穿山甲官方准入 FAQ](https://www.csjplatform.com/supportcenter/28652)

收入公式：`有效展示次数 / 1,000 × 实际 eCPM`。下面 **¥5 / ¥20 / ¥50 eCPM 都是假设场景，不是平台报价**。

| 一次有效广告展示收入           | eCPM ¥5 | eCPM ¥20 | eCPM ¥50 |
| -------------------- | -------:| --------:| --------:|
| 人民币                  | ¥0.005  | ¥0.020   | ¥0.050   |
| 可覆盖约多少次标准 Flash 高峰请求 | 0.32    | 1.26     | 3.16     |

尚未扣 SDK/运营成本，也未计填充失败和广告无效。若每个用户每天两次有效展示、每月 30 天，eCPM ¥20 时约 ¥1.20/月，仍覆盖不了本报告 300 次请求的 ¥4.75。即使播放量不错，也必须看广告展示、AI 消耗和留存之间的真实比例。

待办的价值通常在于快速记完离开；用广告打断每次输入，可能损害核心使用。**现阶段不建议“全免费无限 AI + 广告补贴”作为主模式。** 若未来真有稳定用户，再小规模测试自愿观看换取额外 AI 额度；有网络、可展示、反作弊和剩余额度限制，不能依赖广告保证基本本地功能。

## 8. 给这条路一个有限的验证窗口

当前先停在研究，不自动执行以下步骤。若用户选择继续独立开源，建议限定为一个约两周的试验，而非完成 22 包才让人看：

1. **小范围产品闭环。** 首先只让完成/多选/子项可见性可信，再让手机任务行与全宽详情顺手。单象限放大可作为一个独立小包；暂缓云盘、OEM 笔记直读、Markdown、Planner、开发者模式和多广告网络。先以 Android 为主要验证端，Web 保持现有可用和数据兼容，不同时重做全部打包壳。
2. **试用前让价值可见。** 30–60 秒合成数据演示：一段杂乱任务 → 分类 → 拆目标 → 人工调整 → 勾完成。公开视频可以展示真实操作录屏；交互原型/示例必须标明，不能伪装成已经实现。无 Key 体验可考虑明确标注的演示任务，不偷放共享 Key。
3. **邀请约 20 位目标用户。** 优先找正在做课程项目、毕业/实习准备的人，观察第一次创建/拆解是否无需讲解，七天内是否回来使用、是否真的完成了子步骤。自愿反馈即可，不要求接入个人待办内容的遥测。
4. **分别验证使用与付款。** 星标和视频点赞不当留存；问“过去一周你真的用哪种方法处理这些任务”，再让愿意用的人在 BYOK 和明确标注的托管意向价格之间选择。服务未上线时只收意向，不伪装已可支付。
5. **设停止/缩小条件。** 可用“20 人中至少 8 人无需协助完成首次核心流程、至少 5 人第二周主动回来、至少 3 人明确愿意为省心服务付费”作为小样本方向门槛。这些是预先约定的经验阈值，不是市场统计标准；没达到就访谈原因并收缩，不能靠无限加功能延长试验。

开源作品本身可以在商业验证失败时仍用于实习，但应诚实呈现结果。Bilibili 发布和 GitHub 公开都尚未执行；许可/敏感信息检查与可下载构建应在真正发布前完成。
