# WP15-R：Planner / Schedule 数据与交互契约

状态：研究结论；A1 纯模型与时间规则已实现，见 [WP15_A1_NOTES.md](WP15_A1_NOTES.md)，其余功能待做。基线提交 96ca181320b303f342adafd5964a0c711cfe0fe7，2026-09-29。下文的“决定”是后续 WP15 实现的目标契约，不描述当前产品已经具备的能力；“待定”事项须在相应实现包开工前由产品确认。本研究不更改现有文件格式。

## 现有约束与依据

| 已有事实 | 对 WP15 的约束 |
|---|---|
| [WP14 计划日契约](WP14_NOTES.md)：父任务的 plannedDate 是本地日历日零点，表示打算哪天开始做；deadline 是截止日的 23:59:59，二者独立。plannedDate 不影响象限或紧急性，子项没有 plannedDate。 | 日历中的有时段记录不能重定义这两个字段，也不能顺手改提醒。今天页仍按 [planned_policy.dart](../lib/planned_policy.dart) 分组。 |
| [模型](../lib/models.dart)目前只有 Task、SubTask、Board 和 ExportData；ExportData 当前为 v2。 | 不能把有起止时刻的记录伪装成 plannedDate 或 deadline。时间块与事件需要独立身份和序列化。 |
| [本地保存](DATA_COMPATIBILITY.md)使用 SharedPreferences 的整库双槽提交；[SaveProtocol](../lib/save_protocol.dart)校验完整快照，[Store](../lib/storage.dart)负责事务和导入回滚。 | 日程数据必须参加同一批快照、回滚和恢复；不可用孤立键异步写入。 |
| [备份格式](BACKUP_FORMAT.md)默认导出 v2，导入 v1/v2；[预检](../lib/import_preflight.dart)、[迁移器](../lib/data_migrations.dart)与[分卷导出](../lib/backup_export.dart)共同决定可恢复性。 | 新记录必须贯通预检、合并冲突、分卷和恢复模拟；不能只改模型。旧应用不会保留未知日程字段。 |

## 1. 对象、身份与任务关系【决定】

Planner 是安排任务的入口，Schedule 是按时间查看实际占用的入口；两者读取同一组日程记录，不各存一份。最小模型为顶层 scheduleItems 数组，每条记录有全库唯一且稳定的 id、kind、startAt、endAt、timeZoneId；kind 只能是 timeBlock 或 event。id 与任务 ID 分属不同命名空间。起止是有限范围内的整数 Unix 毫秒绝对时刻，满足 startAt < endAt；端点按半开区间 [startAt, endAt) 解释。记录不是 Task 或 SubTask，不继承完成状态，也不改变任务象限。

| 种类 | 必需字段 | 含义及任务关系 |
|---|---|---|
| 时间块 timeBlock | id、kind、taskId、startAt、endAt、timeZoneId | 为**一个现存父任务**保留工作时间；taskId 必填，不能指向子项。显示时从父任务取标题、所属板和完成状态。一个任务可有多个块。时间块本身没有独立的完成勾选。 |
| 日程事件 event | id、kind、非空白 title、startAt、endAt、timeZoneId，另有 taskId 或 boardId | 有独立标题的日历事项，如会议。可选关联一个父任务：有 taskId 时所属板从该任务派生，不再存 boardId；无 taskId 时 boardId 必填且指向现存板。事件即使关联任务也不代表该任务的工作时间，不参与任务完成计数。 |

关联只通过 taskId 指向父任务 id，不用标题、象限或数组位置。显示时一律解析当前任务，任务改名或跨板移动后随之更新关联显示和板归属。预检拒绝缺失的任务、子项 ID、无效板引用、重复 id、非法 kind/时间戳/时区及关联字段组合，不静默变成独立事件。独立事件随所属板过滤。当前提醒字段 reminderAt 是独立的绝对触发时刻；创建或移动任何日程记录都不创建、取消或改写提醒。

plannedDate、deadline 与日程记录可以同时存在且日期不同；这不是冲突。设置块或事件不自动设置 plannedDate；清除 plannedDate 不删除记录；改变 deadline 不移动记录。Planner 的“待安排”任务来源是父任务列表，Schedule 的占用来源是 scheduleItems。今天页继续使用 WP14 规则，不能因块或事件额外增加一行。完成父任务后，关联记录保留，日历上弱化显示并允许查看；既有记录不被自动清除。日程事件不代替截止日期、计划日或提醒。

示意 v3 数据（字段名与结构为目标契约，不是当前产品格式）：

```json
{
  "scheduleItems": [
    {"id":"block-1","kind":"timeBlock","taskId":"task-1","startAt":1790701200000,"endAt":1790704800000,"timeZoneId":"Asia/Shanghai"},
    {"id":"event-1","kind":"event","title":"评审会","boardId":"board-1","startAt":1790701200000,"endAt":1790704800000,"timeZoneId":"Asia/Shanghai"}
  ]
}
```

## 2. 时间、跨日与重叠【决定】

- 所有记录以绝对时刻存储，用当前设备本地时区渲染日/周网格；同时保留创建或最后明确编辑时间时使用的 IANA timeZoneId，供编辑器解释原来的墙上时间。切换设备时区只改变视图中的时钟标签，不重写 startAt/endAt 或 timeZoneId。时区不可识别时拒绝新建/导入；已保存记录如遇系统时区库变化导致不可识别，保留原始数据并进入可修复状态，不丢弃。实现须在 Android、Windows、Linux 使用一致的 IANA 时区解析规则，而非依赖平台各自对模糊本地时间的默认选择。v3 中禁止只存本地年月日和时分而不存绝对时刻。
- 用户选定本地日期、起止钟点和时区后才解析为绝对时刻。夏令时跳过的本地时刻不存在：编辑器提示并要求重新选时刻，不偷偷顺延。夏令时回拨的重复时刻有两个候选：明确显示 UTC 偏移供选择，并保存选中的绝对时刻；再次打开编辑器须还原同一候选。导入使用现成的 startAt/endAt 和合法 timeZoneId，不用当前时区重新推算。跨夏令时边界允许实际经过时长与墙上钟点差不同；详情显示两端时区/偏移及实际时长。
- 日/周视图按**当前显示时区**的日历边界裁剪记录：某日列与 [当日零点, 次日零点) 有交集才显示该段。恰在午夜结束的记录不占用次日；恰在午夜开始的记录不占用前日。跨日记录在各相交日显示片段，但仍是同一个 id；点任一片段都编辑整条记录。周边界同理。空白全天日期没有虚构的 24 小时长度：跨夏令时日用相邻两个本地零点求边界，可为 23 或 25 小时。
- 允许时间块与时间块、事件与事件及不同种类互相重叠，包括同一任务的多个块；不自动推迟、截断、合并或改写。保存前显示重叠提示，用户仍可确认。网格中并列布局且每条都可点按；重叠不能导致记录被遮挡或不可访问。查询按时间区间相交，不按起始日单独筛选。区间无正时长则拒绝。
- 暂不提供循环事件、全天事件和跨时区旅行排期的专用编辑；跨日的有时段事件已受上述规则支持。单条记录可跨周，视图仍按片段呈现。

## 3. 命令、编辑、删除【决定】

- 新建时间块必须从父任务选择器或任务详情进入；新建事件可以选择关联父任务，也可选择板。创建默认日期可从用户点按的网格位置预填，必须由用户确认；不能将 deadline 当作默认开始时刻。编辑器同时显示计划日、截止日只作参照，保存日程记录时不写它们。
- 拖动块或事件改变起止时刻，拖动整体保持**实际经过毫秒时长**；调整边缘只改变相应端点。拖动以网格当前显示的本地时区解释目标钟点，确认后把 timeZoneId 更新为该时区；表单编辑默认显示记录原 timeZoneId。跨日拖动、在周视图拖动和表单编辑走同一校验与保存命令。夏令时跳过/重复时刻仍执行上节解析规则，遇歧义先在编辑器确认。取消编辑不变更数据；相同值保存为无操作。更改 kind 不提供直接转换；用户须新建另一类记录。
- 删除一条日程记录只删该 id，不删除任务，也不改 plannedDate、deadline、提醒或其他重叠记录。删除父任务时同一事务删除所有关联块和关联事件；独立事件保留。删除板时删除该板任务及其关联记录，并删除该板独立事件。清空板/象限、批量删除和覆盖导入遵守相同的引用清理。将多个任务编组为新父任务时，把原任务关联记录的 taskId 重指向新父任务；撤销编组应恢复原映射。任务删除撤销须恢复任务及其关联记录，不能留下悬空引用。任务完成/取消完成不删或移动记录。
- 保存命令应以 id 和记录修订状态检查过期编辑；同 id 并发修改不得以最后写入静默覆盖。列表和详情共用单一命令入口。导入预览确认后如库已改变，按现有 Store 的重算机制重新校验引用及冲突；失败整批不提交。

## 4. 本地持久化与旧数据【决定】

新增独立的本地快照值 matrixflow-schedule（JSON 数组）；Store 的快照、SaveProtocol 双槽提交、导入事务、失败回滚、启动恢复和测试快照必须把它与任务/板放在同一原子批次。不能靠单独写 SharedPreferences 镜像键使 UI 先于任务持久化。旧槽或旧镜像缺少该键时读为空数组；启动成功后的下一次正常提交写入空数组，不改旧任务的 plannedDate/deadline，也不从它们猜测时间块或事件。已有槽里该键存在但损坏时进入现有恢复流程，不能当成空数组覆盖。

所有删除、编组、跨板移动、撤销和导入路径必须维护引用完整性；本地保存失败时界面要能辨认未持久化状态，重开库不得出现只保存了任务或只保存了日程的半批结果。旧版本可读取带额外快照键的槽，但旧版本重新保存时会丢掉它；因此升级后回退旧可执行文件没有无损保证，发布说明应要求先保留 v3 备份。不能声称 v1/v2 文件可以恢复新增记录。

## 5. 备份、迁移与导入【决定】

文件契约升为 **ExportData v3**，默认导出 v3；导入继续支持 v1、v2，并接受 v3。理由：日程记录是独立顶层集合，旧 v2 读取器会忽略未知字段并在重导出时静默丢失；用 v3 使旧读取器按现有未知版本门禁拒绝文件。现有 [备份格式](BACKUP_FORMAT.md)记录的是当前 v1/v2 行为；实现包落地时再统一更新它和导航。

| 输入或导出 | 目标行为 |
|---|---|
| 导入 v1（含缺省 version）或 v2 | scheduleItems 缺省为空；保留原有任务的 plannedDate/deadline 读取语义。若旧文件碰巧含 scheduleItems，也不把它当作可恢复的日程：预检提示未知字段并忽略；不能默默宣称成功恢复。 |
| 导入 v3 | scheduleItems 必须是数组；空数组合法。校验格式、ID、引用、时区、正时长、数量及文件大小后再预览。未知 kind/非法值/悬空引用阻止提交；未知字段按现有预检策略提示。 |
| 导出 v3 | 完整往返任务、板、日程和配置；默认 UI 文件版本为 v3。分卷时每条日程记录只出现一次，放在首次引入关联任务的卷；独立事件放在首次引入所属板的卷。卷内可同时引入依赖，任务内容继续分块恢复也不重复日程记录；恢复模拟须验证所有 id、引用和内容完全一致。 |
| 显式导出 v2 或 v1 | 只作为兼容用的**有损降级**：省略 scheduleItems，v1 还按 [现有规则](BACKUP_FORMAT.md)省略 plannedDate 等 v2 字段。若库含日程记录，调用方必须明确告知丢失数量并要求确认；设置页不默认提供旧版导出。禁止在无损导出失败时自动退回旧版。 |

覆盖导入用文件中的完整日程集合替换当前集合，缺少集合的 v1/v2 覆盖结果为空；预览列出将删除的记录数。合并时按 id 判断：内容相同跳过、不同即冲突，不能因同 id 的时间或任务不同而覆盖。合并到指定板时，随任务导入的关联记录仍引用同一任务 id，独立事件的 boardId 映射到目标板；关联任务新加入或同 ID 同内容被跳过时可导入该记录，关联任务因缺失、无效板或内容冲突而无法进入结果库时拒绝整批提交，不能留下孤儿。跨卷重复板/记录按现有同 ID 同内容跳过原则处理。覆盖、合并、分卷恢复与失败回滚均需把日程计入预览和恢复结果。v3 必须为记录数量/字节预算设明确上限并实测调整现有 8 MiB 单文件和分卷策略；不能沿用旧容量估计却遗漏日程字节。遇单条过大或无法完整分卷的库，导出明确失败，不产出声称可恢复的文件。

实现时同步修改模型、DataMigrator、ImportPreflight、Store.exportJson、备份分卷与恢复模拟；以同一套规则校验导入和本地读取。v1/v2 原有导入样本仍应通过，未知未来版本继续拒绝。v3 导出的文件不能要求旧版应用读取。

## 6. 日/周视图最小交互【决定】

| 入口/状态 | 最小可验收行为 |
|---|---|
| 范围与导航 | 日视图显示一个本地日历日，周视图周一至周日；可前后翻页、回到今天、切换日/周，保留当前选中日期。显示当前设备时区；网格在 DST 日呈现实际存在的时段并标出重复小时的偏移。 |
| 内容 | 同屏展示时间块与事件，样式和辅助技术名称区分两类；跨日片段有延续提示，重叠项可分别访问。关联记录展示任务标题及板/象限标记；独立事件展示自身标题及板标记。可按当前板或所有板查看，过滤只影响呈现。 |
| 新建与编辑 | 点空白时段可新建块或事件；任务列表/详情可为父任务新建块；点现有记录打开详情并可编辑、删除。保存前显示日期、起止、时区、关联任务/板和重叠提示；表单覆盖触屏无法精确拖动的操作。 |
| 可用性 | 键盘与屏幕阅读器能访问每条记录和表单动作；窄屏、放大字体下不靠仅有颜色区分种类。无记录时仍可选任务或创建事件。加载、写入失败、导入后刷新不显示虚假成功。 |

日/周视图不额外改变今天页分组，也不在这一轮引入月视图、循环规则、外部日历同步或通知投递。

| 包 | 改动边界 | 验收条件 |

| WP15-D：集成与设备验收 | 连接任务入口、平台时区实测、文档导航和发行迁移说明。 | Android、Windows、Linux 预览环境跨时区/夏令时样例与备份恢复通过；全量分析/测试通过；旧版本回退与有损导出提示可见，导航统一更新。 |

## 8. 仍需产品决策【待定；不应在实现时暗中猜测】

1. **板外的全局事件**：本文已决定独立事件必须属于一个板；产品是否需要跨板且不属于任何板的私人事件？若需要，应另定权限、筛选、备份归属和删板行为，不能在当前模型里偷用空 boardId。
2. **时间块的最长跨度及默认时长**：本文只规定 startAt < endAt、可跨日/周，未规定单条最大跨度、点空白时默认结束时间。须在 WP15-C 前确定 UI 默认值和限制；不能让默认值改变已保存数据。
3. **导出容量上限**：新增记录的最大条数、每条标题长度与分卷字节预算须经实测，在 WP15-B 前定量写入文件契约。本文只要求失败可见且恢复无损，不假定旧 8 MiB 估算仍适用。
4. **与第三方日历/通知的关系**：是否以后支持外部同步、提醒或循环事项另开提案；当前日程记录不会自动触发提醒。

上述待定项不阻塞按本文已决定的最小范围实施 WP15-A；产品若扩大范围，应先修订本契约及相应验收条件，不能由实现者自行猜测。
