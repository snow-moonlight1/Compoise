# MatrixFlow OS 集成后最后一轮返修 Implementation Plan

日期：2026-09-25（状态更新于 2026-09-26）。审查基线 `main / 9e30f01`。状态：**RF01 已关闭；RF02、RF05、RF07 的源码和默认回归已集成**，设备定向验收仍归 RF10。依据：[27 包复审报告](OS_IMPLEMENTATION_REVIEW_2026-09-25.md)。本计划接替 09-22 计划的当前派单入口，保留 OS01–OS27 实施历史；不重开所有包，也不新增 OS28。

## 接手规则

1. 只修 Flutter Android/Windows。保持现有视觉、父子层级、48dp 热区、焦点隔离、三协议、JSON v1 读取、四核心键、本地/BYOK。暂停 WP10/WP29/UI 实验，不引入后端、数据库或新状态管理框架。
2. 一次领取一个 RF 包。先读 AGENTS、HANDOFF、当前 git status、本计划和对应报告段；保护他人改动。不擅自 push、发布、创建正式签名或用用户数据做探针。
3. 已复现问题先运行对应 RF-R 反例，再修复并迁入默认 `_test.dart`。源码候选先验证，若反证成立记录“不需修复”及证据，不为了凑工作包改实现。
4. 每包记录基线、修改范围、验证命令/结果、设备/模式、剩余限制，更新本表与 HANDOFF。功能改变后才在 CHANGELOG 顶部追加，纯审查不记成发布。
5. 不以默认 578 测试通过代替专项；也不因为既有设备门槛未齐全要求用户从零重做全部 UX08。尊重用户此前总体认可和本轮 Windows 聚焦反馈，针对受影响路径验收。

## RF01 — Android 聚焦对照

**RF01 关闭结论（2026-09-26）**：用户已确认 Android Release 版本聚焦正常，问题只出现在 Debug 构建；因此归因于构建模式/开发包性能差异，不归因于 Dart 聚焦源码回归。Release 的 `--no-tree-shake-icons` 字库打包修复按现有记录保留。RF01 不再进行源码性能定位；若未来 Release 重新出现卡顿，再另开专项，不回溯修改本包结论。

**范围**：`quadrant_transition_layout.dart`、`animated_task_title.dart`、相邻 pane/card/query；仅测量证据指向某路径时修改它。保留 `MotionPolicy`、字号正确性、焦点/语义修复和父子布局。

1. 基准旧提交 `9d3bbc4` 与审查 HEAD，固定 SDK 3.32.8，同一 Android、同一刷新率、相同 3 父+2 子合成数据，子项展开；冷启动首次与热身后的进入/切换/退出分别采样。用 `scripts/prepare_focus_review.ps1` 建隔离测试程序，说明它只测组件，不代替完整应用。
2. 对照 Debug 与 Profile；完整应用再作 Release 手感验证。记录 APK hash、提交、SDK、设备、刷新率、字体倍率、温度/省电状态与渲染后端。升级只用兼容签名 `install -r`；签名不兼容时停止覆盖，禁止卸载用户应用来规避。
3. 报告 build/raster 帧分位数、超预算帧比例及卡顿所在阶段。按实际刷新率预算（60Hz 16.67ms、120Hz 8.33ms），不得把 totalSpan 或 widget test 耗时当实际 FPS。保存原始合成指标。
4. 若同机同模式确有回退，在独立副本对相关提交分组/二分，优先看 OS02/13/18/19/20 与 SDK 差异；OS22 只改列表不是直接归因。若只 Debug 慢而 Profile/Release 正常，结论写构建模式影响，改测试交付流程即可，不强行重构。
5. 若热路径成立，缩小逐帧重建、复用一次布局结果、未绘制删除线时跳过不必要测量；缓存包含正确 width/style/TextScaler。双重 easing 为旧行为，单独以速度/几何曲线对照决定是否修，不与性能结论混淆。

**原验收要求**：同机基准复测至少三轮，热身后各阶段 build/raster p95 目标在刷新预算内，超预算比例目标 <1%；若硬件无法达成，记录基线、差异、最坏样本及明确例外，不隐藏首次帧。当前关闭依据为用户确认 Android Release 聚焦恢复，且 Debug/Release 差异已明确；不再要求为 Debug 开发包进行源码性能重构。

## RF02 — 导入事务与命令互斥

**入口**：`Store.applyImport`、普通修改命令、SaveProtocol 调用；RF-R01。

确定 Store 层唯一串行提交所有者。导入预览到提交的 revision 校验、凭据步骤、磁盘 commit、内存应用必须遵守同一顺序。可明确拒绝/延后导入中的编辑或按权威状态重算，但不得丢已接受的命令；UI 需解释短暂忙碌并保留输入。仅在 await 后再比较 revision 而磁盘已写入，不算修好。检查旧同步 importData 是否仍能绕过产品约束，必要时限定测试兼容范围。

**验收**：merge/overwrite、双导入、任务编辑/新增/删除/设置变更在每个 await 屏障插入；凭据和槽写失败；预览后变更。每个成功接受的操作出现在最终正确状态；失败不部分改变库。检查内存、flush 后及新 Store 重启读取三者一致，无凭据泄漏。RF-R01 转绿及 OS05–09 回归。

## RF03 — 凭据队列与关闭

**入口**：`updateAIConfig`、CredentialStore、`flush`、退出协调；RF-R02/03。

区分“用户最新意图”“已确认保存值”“队列中值”，只有不存在影响结果的旧写入时才能省略相同值。旧 completion 不覆盖新草稿。提供包含普通保存、凭据与相关导入的 completion/result，退出只在它成功后宣称保存；失败/超时接既有明确选择，不无限等待或偷偷关闭。检查 dispose 后回调与导出显式含 key 的一致性。

**验收**：A→B→空、空→A→空、重复相同值、旧失败/新成功、新失败、读回失败、更新中退出/超时/取消退出；最后意图与 UI、保护存储、重启值一致。RF-R02/03 转绿；不恢复明文普通 prefs；凭据内容不进入日志。

## RF04 — 对称备份契约

**入口**：export/ImportPreflight、文件读写协调及 BACKUP_FORMAT；RF-R04。

先定义支持的库大小与字段上限。保留有界读取及版本化 JSON，选择能恢复本应用支持数据的策略：与实际支持库匹配的限制、分块/流式处理或明确可恢复的分卷方案须有依据。单纯把 4MiB 任意提高、静默截断、只阻止导出而不提供现有大库备份路径均不满足目标。限制需考虑 UTF-8 字节、JSON 包装、旧已存大数据与多次 merge 累积，三语错误和契约同步。

**验收**：界限前/等于/超出、中日文字节、500/10000/50000 数量边界及累积 merge、旧大库、默认无 key/显式含合成 key。所有成功导出的受支持备份能在独立新 Store 预检并完整恢复；取消/超限/写失败不毁原库。RF-R04 转绿。

## RF05 — 请求状态闭环

**入口**：TestConnectionButton / ModelRequestSession；RF-R06。

将身份变化、取消、generation 和 busy/result 的转换放到明确 session 生命周期，避免 build 内只失效 ticket 却保留 busy。旧响应不能覆盖新结果，每条完成/取消/失败路径都可恢复操作；需避免旧 finally 清掉新请求 busy。

**验收**：首次、重测、生成测试过程中分别改 URL/key/protocol/model，切换页/关闭页，超时/异常/取消，旧响应晚于新响应。按钮可继续使用，无已释放 widget 写入，无隐式付费生成。RF-R06 转绿；OS10/11 回归。

## RF06 — 能力与探测语义

**入口**：ai_capabilities、ai_service 请求与探测；RF-R07。

用具体模型版本及准确端点/用户显式能力声明区分能力；未知版本保守省略参数并说明不能强制关闭。原始 GPT-5 不发 none；不能用一个 Responses 枚举推断所有模型支持。核对 DeepSeek 自定义反代与 Anthropic 正则覆盖边界，保留三协议。短探测若只得到 reasoning 或 length 截断，应返回可理解的部分成功/不足结果，而非认证失败；预算和可能费用需保持显式。

**验收**：原始 GPT-5、5.1、未知家族、o 系列、官方 DeepSeek、自定义同名模型但不支持扩展端点、已知/未知 Anthropic 的 mock body 与结果分类；RF-R07 转绿。依据仅用厂商官方文档，记核查日期；真实付费调用若没有凭据/授权保持未测。

## RF07 — 输入与草稿

**入口**：TaskEditDraft、TaskDetailPanel、子项编辑、相关关闭/切换协调；RF-R05。

有效且非折叠 composing 才是待提交；确认标题、笔记和子项实际提交路径一致。补 widget 复现“只输入新子项但没按添加，关闭或切换任务”，定义其 dirty/保存/丢弃行为，防止带到另一任务或无提示遗失。保持已实现的字段级合并，不整任务覆盖远端于编辑期间的本地更新。

**验收**：TextRange.empty、折叠合法范围、非空 composing、中文/日文完成输入；回车、保存、关闭、切换、删除任务、未添加子项、取消关闭。RF-R05 转绿，Android 软键盘与 Windows IME 定向人工补测。

## RF08 — 提醒重试边界

**范围**：ReminderService 账本、Store 启动 reconciliation；先建立反例，报告中目前是源码风险。

模拟至少六次“加载→rescheduleAllFuture 失败→reconcile→持久化→重启”，检查 attempts/首次失败时间是否被清零。真实用户更改提醒可开启新一代任务，单纯启动重试不能重置上限。注入账本写失败/延迟、64 项满额、清除与异步 load 相交，检查错误是否可见及幽灵提醒是否丢失追踪。将必须落地的账本操作纳入明确 completion，必要时与 RF03 退出协调，但不宣称平台通知绝对可靠。

**验收**：次数与 TTL 有界、已删除/已完成/改期不复活；失败与溢出可解释，不静默当成功；取消重试保留正确通知身份。用持久化再创建 service 验证，最后补 Android 未来排程/取消与 Windows 运行中提醒定向记录。

## RF09 — 保存/查询成本

**范围**：Store 查询只读容器、`_saveTasks/_write/_snapshotValues`；不做整体架构重写。

先测 3/100/1000/10000 合成记录的局部编辑、设置输入、批量操作与聚焦，区分命令同步编码时间、队列保存、widget build。去掉被丢弃的 JSON 入参和无必要重复整库编码，查询按有效 revision/字段失效规则复用结果或稳定只读视图。保留 snapshot 隔离与顺序/失败语义；不把可修改 backing list 泄漏到页面。

**验收**：相同正确结果下编码/分配/延迟下降；保存失败/重试、退出、导入并发回归不退化；测不出收益则有据延期。不得用“卡顿优化”名义删除无障碍、动画或持久化可靠性。

## RF10 — 验收、文档与交付

确认各包源码与默认回归集成；固定 SDK 跑 `flutter test --no-pub`、`flutter analyze --no-pub`，新反例全部有默认回归归属。针对本轮影响补 Android Release 3+2 聚焦/编辑/导入/凭据/提醒，以及 Windows Release 聚焦/键盘/IME/退出；额外验证桌面 applySettings 未完成时退出不重新创建托盘/热键。实际未测如实登记。

更新 AGENTS/HANDOFF/ARCHITECTURE/备份与开发说明，区分 Debug 开发包、Release 性能测试包、正式签名发行包。保留用户 OS 前总体认可与本轮 Windows 聚焦认可；Android Release 是否认可按实际反馈。正式 keystore、公开 remote、托管 CI、下载渠道、升级验收沿 OS26 单独处理，没有材料不伪造完成，也不无限扩大返修范围。
